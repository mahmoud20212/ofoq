## النطاق والإتاحة

أعيد استخدام `LabRun` والموصل `Judge0Client`؛ لا اعتماديات أو broker جديد، ولا تنفيذ كود
داخل Django. قاعدة البيانات هي طابور العمل الدائم، والعامل عملية CLI مستقلة عن طلب الويب.
لا UI أو «تحقق من الحل» أو تغيير للتقدم والشهادات. `accepted` هنا يعني انتهاء برنامج
الطالب دون خطأ، وليس صحة حل التحدي؛ لا يكتب هذا المسار `ChallengeSuccess` إطلاقًا.

`LAB_RUN_API_ENABLED=False` و`LAB_RUN_WORKER_ENABLED=False` في الإعدادات العادية.
المسارات تعيد 404 قبل الوصول للجداول إذا كانت الإتاحة مغلقة. تفعلهما
`educa.judge0_preview_settings` في قاعدة المعاينة فقط؛ لا تفعلهما للطلاب قبل القبول.
الترحيل الإضافي `0021_lab_run_queue` لم يُطبق على قاعدة المشروع الفعلية، بل على الاختبارات
وقاعدة المعاينة فقط. لا تعديل لترحيلات قديمة أو إعدادات هوية أو بيانات فعلية.

## عقد HTTP

### إنشاء تشغيل

`POST /lab/challenges/<challenge_id>/runs/`

يتطلب جلسة طالب نشطة وCSRF و`Content-Type: application/json`. تُرفض الحقول غير المعروفة
والمفاتيح المكررة وJSON غير الصالح. اسم cookie الحالي `masar_csrf`، والترويسة `X-CSRFToken`.

```json
{
  "request_id": "7c965910-fcdb-4777-980f-7d5ac9623a54",
  "code": "a,b=map(int,input().split()); print(a+b)",
  "stdin": "2 3\n"
}
```

أو بدّل stdin بـ`"example_id": 1`، ولا ترسلهما معًا. تُقرأ مدخلات المثال من أمثلة **النسخة
المنشورة الحالية** فقط؛ لا اختيار حالات اختبار مخفية أو أمثلة مسودة. كل مثال في ChallengeExample
عام بطبيعته؛ الاختبارات المخفية في جدول آخر لا يُقرأ هنا.

رد القبول `202 Accepted` يتضمن `Location` و`status_url` و`run_id` و`created=true` وحالة queued.
لا توجد مكالمة Judge0 داخل مسار الإنشاء. تُثبت اللغة والإصدار والكود والمدخلات وحدود الموارد
وهوية النسخة وexecution profile قبل الرد. لقطة `purpose=run` مختصرة، ولا تنسخ الحل المرجعي
أو الحالات المخفية؛ توافق اللقطات القديمة الكاملة محفوظ دون إعادة كتابة التاريخ.

نفس request_id **للطالب نفسه** ونفس البيانات يعيد `200` و`created=false` والسجل ذاته، حتى
بعد انتهاء التشغيل. تغيّر الكود أو المدخل أو المثال أو التحدي بالمفتاح نفسه يعيد `409 request_id_conflict`.
المفتاح مستقل بين طالبين. استخدم UUID جديدًا فقط عندما يقصد الطالب تجربة جديدة، وليس لمجرد إعادة الطلب.

### الحالة والنتيجة

`GET /lab/runs/<run_id>/`

الصاحب فقط؛ مستخدم آخر يحصل على 404، وانتهاء الجلسة 401. تُفحص الصلاحية مجددًا في كل قراءة.
هذه قراءة من قاعدة البيانات فقط، فلا تعتمد على بقاء الصفحة أو اتصال الطالب أو اتصال Judge0.
تحتفظ الواجهة اللاحقة بـrun_id/status_url؛ ويمكن إعادة طلب الإنشاء بنفس المفتاح والبيانات
لاستعادة المعرّف بعد فقد رد القبول. لا تُنشأ مهمة بديلة تلقائيًا.

مثال نتيجة مختصر؛ حقول التوقيت قد تكون null عندما لا تتوفر الملاحظة:

```json
{
  "run_id": 2,
  "status": "finished",
  "phase": "complete",
  "terminal": true,
  "verdict": "accepted",
  "verdict_label": "انتهى التشغيل دون خطأ",
  "backend_status": "finished",
  "status_label": "انتهى التشغيل",
  "needs_operator_review": false,
  "error_code": null,
  "error_message": null,
  "language": {"name": "Python", "version": "3.8.1"},
  "queue_seconds": 0.051102,
  "cpu_seconds": "0.021000",
  "observed_execution_seconds": null,
  "memory_kb": 3260,
  "stdout": "5\n",
  "stderr": "",
  "compile_output": ""
}
```

الرد يشمل أيضًا request_id وcreated_at وfinished_at. لا token أو reference_solution أو
private_result أو hidden tests أو إعدادات الاتصال في الرد. stdout/stderr/compile_output
نصوص ضمن مجموع سقف بايتات المخرجات، وليس HTML؛ الواجهة اللاحقة ملزمة بـtextContent/escaping.
أخطاء الخدمة تعرض رسائل ثابتة ولا تعيد جسم upstream أو message الداخلي. الردود خاصة وno-store.

الحالات الأساسية queued/running/finished/failed؛ phase يميز queued/dispatching/submitted/
uncertain/complete/error. backend_status يميز انتظار Judge0 عن التنفيذ عندما لوحظ.
verdict يميز compile_error/runtime_error/time_limit/memory_limit/output_limit/system_error.
`uncertain` حالة غير محسومة، ليست نجاحًا أو إجابة خاطئة؛ تحتاج المشغّل ولا يسمح بإعادة POST آلية.

الأخطاء: 400 مدخلات غير صالحة، 401 دخول مطلوب، 403 CSRF/صلاحية، 404 عدم إتاحة/ملكية،
409 تعارض المفتاح/الجاهزية، 413 حجم، 415 نوع المحتوى، 429 معدل أو تزامن، 503 توقف/إعداد تنفيذ.
أخطاء التطبيق JSON برمز ورسالة آمنة؛ فشل CSRF قد يعيده middleware بصفحة Django 403 المعتادة.

## الحدود والقفل

`LAB_RUN_LIMITS`: تشغيلان نشطان لكل طالب، و16 إجمالًا، و10 طلبات مقبولة لكل طالب خلال 60 ثانية.
المكرر المطابق لا يستهلك حصة جديدة. الحالات المجهولة تحتفظ بحصة التزامن حتى تُراجع، كي لا يسمح
فقد رد الإنشاء بتجاوز السقف. rate يحسب المقبول حتى لو انتهى سريعًا أو بفشل خدمة.
هذه حدود تطوير أولية وليست سعة إنتاج مثبتة؛ يجب مواءمتها مع سعة Judge0 والـqueue عند القبول.

الكود حتى 100000 محرف و400000 بايت، والمدخل حتى 65536 بايت، وجسم JSON حتى 600000 بايت،
مع تطبيق حدود الاتصال الأصغر إن ضُبطت. CPU/memory/output من النسخة والسقوف المركزية فقط.
لا language_id أو version_id أو student_id أو resource/network/compiler options من المتصفح.

صف `LabRunQueueControl` الواحد يقفل القبول وعدّ الحصص والادعاء بين العمليات.
تُحجز كتابة SQLite قبل قراءة العدادات، وselect_for_update في قواعد تدعمها؛ قيود UUID تمنع التكرار.
كل الشبكة خارج المعاملات. قفل الدورة/التحدي الحالي يعاد استخدامه عند القبول، ولا تُبنى سياسة
منهج/نشر موازية. التزامن اختُبر على SQLite باتصالين وخيطين، لا PostgreSQL أو أحمال موزعة.

## تشغيل العامل وإيقافه

من `educa`، بأداة Python البيئة الحالية:

```text
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings
```

للعمل المحدود/التشخيص، وليس الانتظار حتى نهاية كل مهمة:

```text
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --once --limit 16
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --once --limit 1 --run-id 2
```

Ctrl+C أو SIGTERM يطلب إيقافًا هادئًا بعد خطوة الشبكة المحدودة الحالية. لا توقف Judge0 أو
النفق أو خدمات أفق لإيقاف هذا العامل. القتل المفاجئ يترك السجل/lease للاستعادة بعد انتهائها.
لا تتغير سياسات النظام أو تُثبت خدمة OS تلقائيًا. لم يُترك عامل دائم شغالًا في هذه المهمة.

إيقاف مؤقت إداري (قبول جديد وإرسال محلي جديد)، ثم الاستئناف:

```text
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --pause
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --resume
```

GET والمكرر المطابق يظلان متاحين، وتستمر متابعة tokens الموجودة؛ pause ليس إلغاءً لما أُرسل.
الأوامر الإدارية لمشغّل المضيف الموثوق، ولا يوجد مسار HTTP للطلاب لتغييرها.

## التسليم والاستعادة

الادعاء يثبت lease UUID وتاريخ انتهاء (120 ثانية افتراضيًا، تُرفع لتغطي مهلات الاتصال)،
ويسجل dispatching **قبل** الاتصال. تحديثات العامل مشروطة بملكيته للـlease كي لا يكتب عامل قديم
فوق عامل أحدث. تُحفظ token وsubmitted في تحديث دائم فور استلام الرد.

- queued: عامل واحد يدعيها ثم يتحقق من الاتصال والإصدار والإتاحة والانتساب قبل أول إرسال.
- submitted/token محفوظ: العامل الجديد يستعلم بـGET فقط بعد تحرر/انتهاء lease، ولا يعيد POST.
- dispatching بلا token وlease منتهية: تتحول إلى uncertain؛ لا إعادة إرسال تلقائية حتى لو كان
  الانهيار قبل الإرسال فعليًا، لأننا لا نستطيع الجزم. لا وعد exactly-once بعد ضياع رد POST.
- فشل GET: يحتفظ بالـtoken ويؤجل المتابعة 2–16 ثانية، دون عدّه إجابة خاطئة أو نجاحًا.
- انتظار بعيد أو انقطاع لمدة تتجاوز 1800 ثانية: uncertain مع token للمراجعة بدل المتابعة بلا حد.
- خروج/تعطيل اللغة بعد الإرسال لا يمحو المهمة؛ يمكن متابعة token المعلوم. تغير هوية الخدمة/
  profile يوقف المعالجة بخطأ آمن بدل إرسال الكود إلى خدمة مختلفة.

أوامر التسوية بعد مراجعة المشغّل فقط:

```text
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --retry-poll RUN_ID
..\.venv\Scripts\python.exe -B manage.py lab_run_worker --settings=educa.judge0_preview_settings --abandon-uncertain RUN_ID --reason "سبب التسوية بعد فحص المهمة البعيدة"
```

retry-poll لا يعمل إلا مع token محفوظ ويستأنف GET فقط. abandon يسجل السبب وفشل خدمة ويفرغ
الحصة؛ لا يُستخدم قبل تسوية احتمال استمرار المهمة البعيدة. لا يعيد تشغيلها ولا يحذف التاريخ.
بلا token يلزم تصالح تشغيلي خارج الطلب؛ لا نخمن token أو نبحث في بيانات مستخدمين آخرين.

## الوصول والأرشفة

القبول يعيد استخدام challenge_for_execution: عام منشور معتمد أو تحدي دورة منشور لملتحق.
لا تنفيذ لمسودة أو نسخة معلّم. الدورة المؤرشفة تبقى متاحة للملتحق وفق السياسة الحالية.
أرشفة التحدي تمنع الطلبات الجديدة وتبقي السجلات؛ المهام المقبولة قبلها تستكمل بلقطتها.
قراءة التاريخ تحتاج مالكه النشط، واشتراكه الحالي إذا كان من دورة، ولو كانت مؤرشفة.
فقد الاشتراك يمنع القراءة والإرسال غير المبدوء؛ عملية بعيدة بدأت بالفعل قد تنتهي دون كشف نتيجتها
لمن فقد الوصول. إعادة النشر لا تغير اللقطة أو تمنع قراءة التشغيل القديم المسموح.
حذف مصدر النسخة يبقي التاريخ؛ إذا حُذفت هوية التحدي نفسها إداريًا، تفشل قراءة الطالب مغلقة
لعدم إمكان إعادة فحص الاستحقاق، ويبقى السجل للإدارة.

## التحقق — المحاكاة منفصلة عن التشغيل الحقيقي

تشغيل DiscoverRunner على قاعدة SQLite بالذاكرة وملفات مؤقتة وكاش/قنوات/بريد معزولة:

- `courses.tests_lab_runs`: **28 ناجحًا**، منها ثلاثة اختبارات تزامن فعلية بقاعدتي اتصال.
- `courses.tests_judge0` و`courses.tests_lab_services` و`courses.tests_lab_models`:
  مع المجموعة السابقة **106 ناجحة، صفر فشل وصفر تخطٍ**.
- تشمل CSRF، المصادقة والملكية والالتحاق والمسودات والمؤرشفات، المفتاح المطابق والمتعارض،
  الأحجام والحصص، pause، عاملين، انهيار بعد token، dispatch مجهول، تراجع GET، انتهاء المتابعة،
  منع التسريب وحجم النصوص، وعدم إنشاء نجاح تحدٍّ. Judge0 في هذه الاختبارات محاكى بالكامل.
- فحص Django سليم و`makemigrations courses students --check --dry-run` لا يقترح تغييرات.

**التشغيل الحقيقي** على خدمة AWS الحالية عبر النفق، باستخدام Python 3.8.1 وتحدي جمع عددين
الاصطناعي ذي الفحص المرجعي الناجح، واعتماده داخل المعاينة بالإجراءات الحالية ومراجع مختلف عن المنشئ:

1. خادم HTTP مؤقت على loopback بمنفذ حر وجلسة طالب اصطناعي وCSRF، بلا تغيير SSO.
2. POST عاد 202 خلال **0.0905 ثانية تقريبًا**؛ السجل queued بلا token قبل بدء العامل.
3. إعادة نفس الطلب عادت 200 بالسجل نفسه. العامل الأول حفظ token وترك المهمة submitted.
4. عامل Python جديد استعادها GET، وأعاد `accepted` وstdout=`5\n`. سجل النقل الحقيقي:
   العامل الأول **POST واحد و4 GET**، والعامل الجديد **صفر POST وGET واحد**.
   استُخدمت PIDs المرصودة داخل Python لأن Windows venv launcher له PID مختلف عن العملية الفعلية.
5. قراءة النتيجة عبر اتصال HTTP جديد، دون اعتماد على الطلب/الصفحة الأصلية. لم يُكتب ChallengeSuccess.
6. تحقق حقيقي مستقل للّقطة المختصرة النهائية والمثال الظاهر: POST واحد وaccepted و`5\n`،
   ولا حل مرجعي أو اختبارات مخفية في لقطة LabRun الجديدة.

التقارير والتتبعات الاصطناعية داخل `.local` المستثناة من Git. أُوقف خادم المعاينة المؤقت
والعاملان انتهيا، وحُذفت جلسة HTTP التجريبية؛ بقيت سجلات التشغيل للمراجعة.
بصمة قاعدة المشروع الفعلية بقيت مطابقة. لم تُطبق الترحيلات عليها.

القياس الواحد ليس اختبار سعة أو ضمان زمن استجابة. لا اختبار PostgreSQL أو انقطاع واسع موزع
أو تعطل مضيف AWS ضمن هذه المهمة. القبول البصري وربط زر الطالب وتشغيله العام مؤجلة،
كما أن «تحقق من الحل» وتسجيل النجاح مهمة منفصلة.
