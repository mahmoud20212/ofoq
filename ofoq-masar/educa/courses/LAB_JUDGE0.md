## التقييم التلقائي الفعلي — 2026-11-19

أُضيفت خدمة «تحقق من الحل» باستخدام موصل Judge0 والعامل الدائم الموجودين؛ التفاصيل في
[LAB_SUBMISSIONS.md](LAB_SUBMISSIONS.md). نجحت 134 حالة معزولة، منها 28 للتقييم، مع
تجربة فعلية مستقلة على AWS عبر النفق الحالي وHTTP محلي بمعاينة منفصلة:
حل جمع صحيح اجتاز الحالتين وأنشأ إنجازًا واحدًا، وحل يستخدم `abs(a)+b` اجتاز الظاهرة
وفشل في المخفية، دون كشف بياناتها أو أخطائها في استجابة الطالب. بقي الإنجاز السابق محفوظًا.
استُرجعت نتائج الحالات الأربع في عمليات عامل جديدة: **4 POST فقط، واحد لكل حالة**.
قراءة المحاولة من طالب آخر عادت 404. لم تتغير قاعدة المشروع أو الهوية أو خدمة AWS.
الترحيل 0022 طُبق على المعاينة فقط، والإتاحة العامة ما زالت مغلقة.

## طابور «تشغيل» — 2026-11-19

أضيف طابور دائم يعتمد `LabRun` والموصل نفسه، دون طابور «تحقق من الحل» أو واجهات.
التفاصيل والمسارات وأوامر التشغيل والاستعادة في [LAB_RUNS.md](LAB_RUNS.md).
نجحت 106 اختبارات معزولة، منها 28 للطابور، ثم رحلة فعلية عبر HTTP محلي وعاملين
بعمليتي Python مستقلتين وJudge0 على AWS. عاد الطلب بـ202 خلال نحو 91ms، وأعاد
المعرّف المكرر السجل نفسه. حفظ العامل الأول token، واسترجع الثاني النتيجة `5` بعملية
GET فقط: POST واحد إجمالًا وصفر POST بعد إعادة تشغيل العامل. كان backend قيد التنفيذ
بين العمليتين، فهذه استعادة فعلية من سجل دائم وليست نتيجة محاكاة.
تلا ذلك تشغيل فعلي مستقل للمثال الظاهر باللقطة المختصرة الجديدة: POST واحد ونتيجة `5`.
لا نسخ للحل المرجعي أو الاختبارات المخفية في لقطة التشغيل الجديدة، ولا سجل «تم الحل» في التجربتين.
قاعدة المشروع الفعلية بقيت دون تغيير، والترحيل 0021 طُبق على المعاينة فقط.
الإتاحة للطلاب والعامل مغلقان في الإعدادات العادية؛ مفعّلان صراحة داخل المعاينة فقط.
فحوص التزامن والتعطل والأخطاء والحدود بالمحاكاة مستقلة عن هذه النتائج الحقيقية.

## فحوص تشغيلية فعلية عبر AWS ونفق SSH — 2026-11-19

هذه النتائج أحدث من تقريري 2026-11-18 و2026-11-16 أدناه؛ أبقيناهما كسجل تاريخي.
استُخدمت الخدمة المخصصة الحالية عبر النفق الموجود وإعدادات `educa.judge0_preview_settings`،
دون إعادة تجهيز الخدمة أو تغيير إعداداتها. API 1.13.1 وPython 3.8.1، مع سجل مراجعة عزل
موجود وإعدادَي `enable_network=false` و`allow_enable_network=false`.
اعتمدنا نتائج تشغيل اللغات الثلاث والفحص المرجعي السابق؛ لم نعد تشغيلها أو ننشئ أدلة بديلة لها.
لا تشغيل عام أو بيانات خاصة، ولا تغيير لطابور الطلاب أو إتاحة المختبر لهم.

السكربت ذو الاستخدام الواحد والتقرير التفصيلي داخل `deploy/judge0/.local/` المستثناة من Git:
`operational-probe-2026-11-19.py` و`operational-results-2026-11-19.json`.
يحفظ السكربت حالة dispatching ثم token فور استلامه، ويرفض إعادة التجربة تلقائيًا إذا كان التقرير
موجودًا. استُخدم `Judge0Client` و`HTTPTransport` الموجودان، مع تسجيل طريقة كل طلب دون أسرار.
حُفظت معرّفات العمليات محليًا ولم تُعرض بيانات الاتصال أو المفاتيح في التقرير العام.

### 1. حد المخرجات: طُبق في الخدمة والموصل

- برنامج Python محدود حاول طباعة **131072 بايت (128KiB)**، بسقف **65536 بايت (64KiB)**،
  وCPU ثانيتين وذاكرة 262144KiB. لم يُستخدم طبع غير محدود أو ضغط على المضيف.
- استجابة Judge0 النهائية: status **11 / nonzero exit code**، وexit code **1**،
  وstdout بطول **65536 بايت بالضبط**؛ stderr بطول 145 بايت يتضمن
  `OSError: [Errno 27] File too large`. حد الملف منع اكتمال الكتابة فخرج البرنامج بخطأ.
  هذه ليست استجابة status 8 أو إثبات أن العامل قتله بإشارة؛ النتيجة المحددة هنا حد ملف فعّال.
- الموصل أعاد **`finished / output_limit`** بدل accepted؛ مجموع المخرجات المفكوكة
  (stdout مع stderr) تجاوز 64KiB. لم يصل النقل إلى سقف استجابة HTTP البالغ 4MiB.
- أُعيد GET لنفس token بسقف استهلاك أدق **1024 بايت**، فأعاد الموصل output_limit أيضًا،
  دون أي تنفيذ جديد. هذا فحص مستقل لحد الموصل، لا ادعاء أن سقف المهمة الأصلية كان 1KiB.
- النتيجة: حد الخدمة وحد المخرجات لدى الموصل عملا في هذه التجربة، والحالة النهائية واضحة
  وليست نجاحًا وهميًا. لم تُضف واجهة جديدة لعرضها ضمن هذه المهمة.

### 2. عزل الشبكة: تحكم إيجابي ومستمع واحد فقط

- أُنشئ مستمع TCP مؤقت تحت سيطرتنا في **namespace الشبكة الخارجية لحاوية العامل**،
  مربوطًا بـ`127.0.0.1` ومنفذ اختاره النظام؛ لم يُنشر منفذ على AWS أو Windows أو الإنترنت.
- نقطة التحكم كانت عملية موثوقة داخل حاوية العامل، خارج isolate: اتصلت بالمستمع نفسه،
  أرسلت علامة اصطناعية وتلقت acknowledgment؛ سجل المستمع وصول علامة التحكم.
- برنامج Python عبر Judge0 حاول الاتصال بنفس العنوان والمنفذ مرة واحدة بمهلة ثانية واحدة.
  أعاد `reachable=false` وOSError، ولم يسجل المستمع أي علامة من برنامج التنفيذ.
- لم تُختبر أي وجهة غير المستمع التجريبي، ولا بيانات اعتماد أو metadata أو خدمات أفق.
- ما يثبته ذلك: الفصل عن مستمع loopback العامل في مسار التنفيذ المختبر، بعد إثبات صلاحيته
  من نقطة التحكم. لا يثبت وحده منع كل وجهات الخروج أو كل البروتوكولات أو مقاومة اختراق
  حاوية privileged. فحص firewall والمضيف والوجهات الأخرى ليس ضمن هذه التجربة.

### 3. عزل ملفات التطبيق: ملفات اصطناعية فقط

- أُنشئ ملف sentinel محلي داخل مجلد المعاينة، ونسخة اصطناعية في مجلد مؤقت فريد تحت
  `/tmp/ofoq-lab-probe-<nonce>/` **خارج isolate داخل العامل** لمحاكاة بيانات التطبيق الخارجية.
  ملف العامل مقروء 0644 والمجلد 0755؛ لم يُستخدم منع أذونات مقصود لإنتاج فشل مضلل.
- قرأت نقطة التحكم الملف الخارجي بنجاح وتحققت من علامته الاصطناعية، كما ثبتت قراءة
  ملف المعاينة من مضيف التطبيق. لا قراءة لأي ملف حقيقي أو سر للتطبيق.
- برنامج Judge0 حاول فتح المسارين الاصطناعيين المحددين فقط؛ كلاهما أعاد
  `FileNotFoundError` ولم تُقرأ العلامة.
- ما يثبته ذلك: عدم ظهور sentinel العامل الخارجي في صندوق التنفيذ الحالي؛ وعدم توفر ملف
  مضيف التطبيق المحلي ضمن التنفيذ على AWS. اختبار مسار Windows على Linux وحده ليس
  برهان عزل قويًا، لذلك استُخدم أيضًا ملف العامل مع التحكم الإيجابي داخل البيئة نفسها.
  هذا ليس تدقيقًا شاملًا للـmounts أو أمان المضيف privileged أو أذونات ملفات التطبيق الفعلية.

### 4. استرجاع token بعد انقطاع اتصال فعلي

- أُرسلت مهمة اصطناعية واحدة تطبع `recovery-ok` وحُفظ token قبل قطع الاتصال.
- أُنشئ **نفق اختبار إضافي مملوك للتجربة** إلى الخدمة نفسها، وثبت الاتصال به. أُوقف هذا
  النفق فقط مؤقتًا، ففشل GET حقيقي بـ`connection_failed`؛ لم تتوقف الخدمة أو النفق الأصلي.
- أُعيد فتح نفق الاختبار نفسه، ثم GET بالـtoken المحفوظ: النتيجة `accepted` والناتج
  `recovery-ok`. عدد POST في سجل الطلبات قبل الانقطاع وبعد الاسترجاع **4 ثم 4**،
  أي **صفر POST إضافي** أثناء الاسترجاع. المجموع أربع مهام للفحوص الأربعة كلها.
- النتيجة تثبت الاسترجاع عندما يكون token محفوظًا. لا تختبر ضياع رد POST الأول قبل حفظ
  token أو تسوية حالة uncertain، ولا انقطاع العامل أو قاعدة Judge0 نفسها.

### التنظيف وحدود النتيجة

أُغلق نفق الاختبار الإضافي، وأوقف المستمع المؤقت وحُذفت ملفاته ومجلده المحدد وملف sentinel
المحلي. سجل المستمع النهائي يحتوي علامة التحكم فقط. جميع المهام الأربع وصلت إلى حالة نهائية.
بصمة SHA-256 لقاعدة المشروع الفعلية بقيت مطابقة قبل الفحوص وبعدها؛ لا ترحيلات أو تغييرات
بيانات فعلية أو إعدادات Keycloak أو شبكة الخدمة أو خدمات أفق. لم تُضف طوابير أو واجهات.

الفحوص الأربعة نجحت ضمن نطاقها المحدد. تبقى مراجعة امتيازات الحاويات والمضيف وfirewall
والـmounts والمراقبة والأحمال والتعافي من ضياع token خارج ما أثبتته هذه التجربة.
نجاحها ليس تدقيقًا أمنيًا شاملًا ولا تفعيلًا تلقائيًا لتشغيل الطلاب؛ طابور الطلاب مهمة لاحقة.

## التحقق التشغيلي — 2026-11-18

**الحكم: الخدمة غير جاهزة بعد لبدء التحقق الفعلي من طابور الطلاب.**
جُهزت ملفات التشغيل والمعاينة؛ لم تعمل خدمة Judge0 ولم تنفذ برامج فعلية.
تعليمات التشغيل المفصلة في [deploy/judge0/README.md](../../deploy/judge0/README.md).

- Docker Client 29.7.2 وCompose v5.5.1 متاحان. الفحص خارج قيود البيئة أكد أن
  محرك `dockerDesktopLinuxEngine` غير متاح وأن توزيعة WSL2 `docker-desktop` متوقفة.
  لذلك تعذر فحص kernel/cgroup أو تشغيل الحاويات. لا افتراض أن المشكلة مجرد صلاحيات الأداة.
- لم يبدأ Docker Desktop أو WSL، ولم يتغير GRUB أو cgroups أو سياسة PowerShell أو Keycloak
  أو أي خدمة أفق. توثيق الإصدار يتطلب Linux، ويوصي Ubuntu 22.04 وإعداد cgroup v1.
  يلزم مضيف/آلة Linux مخصصة مناسبة؛ تغيير إعدادات جهاز مشترك ليس جزءًا من التنفيذ التلقائي.
- صورة Judge0 CE 1.13.1 الرسمية موجودة في السجل بمعمارية Linux amd64 وثُبتت ببصمتها:
  `sha256:6b5d6a66aa19a8e878a52ea3c6a560afc1086734d96e2885b561fd5c6018f082`.
  فحص manifest قراءة فقط؛ لم تُسحب أو تُشغّل الصورة، ولم تُرفع صور أو ملفات خاصة.
- أضيف `deploy/judge0/compose.yaml`: مشروع وشبكة داخلية وبيانات مستقلة، وAPI على
  `127.0.0.1:2359` فقط، دون منافذ PostgreSQL/Redis أو mount لملفات التطبيق.
  نجح `docker compose ... config --quiet`، وهو فحص صياغة وليس اختبار خدمة.
- متطلب upstream الفعلي هو privileged لكل من server وworkers. بقي موثقًا وصريحًا؛
  لا يعد Docker أو internal network ضمانًا ضد وصول حاوية privileged إلى مضيفها.
  يُطلب مضيف تطوير منفصل بلا أسرار أفق، ومراجعة العزل والتحديثات قبل تنفيذ الكود.
- `prepare.py init` أنشأ أسرار API/Redis/Postgres/Rails محليًا داخل `.local` المستثناة من
  Git، دون عرضها أو تعديل `.env.local`. إعادة init لا تدور الأسرار ولا تستبدلها.
- `prepare.py preview` طبّق الترحيلات على `deploy/judge0/.local/preview.sqlite3` فقط،
  مع وسائط وكاش وقنوات وبريد مستقلين. أُنشئ مشغّل CLI تجريبي برقم 1، دون كلمة مرور قابلة
  للاستخدام أو superuser، وبصلاحيات التشغيل والمراجعة الضيقة. لا تسجيل دخول تجريبي أو تجاوز SSO.
- `educa.judge0_preview_settings` لا تغيّر إعدادات التطبيق العادية؛ تُمرر صراحة للأوامر.
  لا توجد علامة مراجعة عزل مصطنعة: `sandbox-review.txt` غير منشأ، فيرفض الموصل إرسال كود
  حتى توجد مراجعة فعلية، إضافة إلى فحوص config لدى الخدمة.
- محاولة اتصال حقيقية عبر `lab_judge0 ... inspect --engine judge0-dev` عادت بخطأ اتصال
  لأن الخدمة غائبة؛ لم تُسجل كإجابة خاطئة أو فحص ناجح. لم يُختبر التعطل أثناء تنفيذ قائم.
- سكربت `manage.ps1` اجتاز تحليل الصياغة، لكن سياسة PowerShell المحلية تمنع استدعاءه مباشرة.
  لم تتغير السياسة. أوامر Compose المباشرة موثقة، وسكربت Up يتحقق من Linux amd64/cgroup v1
  ويرفض التشغيل دون إقرار مراجعة مضيف مخصص. أوامر الإيقاف مقيّدة بهذا المشروع وتحفظ البيانات.
- أعيد تشغيل **25 اختبار محاكاة: كلها ناجحة، دون فشل أو تخطٍ**؛ لا تعني تشغيلًا حقيقيًا.

## الحالة التشغيلية — 2026-11-16

لم توجد إعدادات Judge0 مخصصة في بيئة المشروع أو ملف البيئة المحلي أو compose عند الفحص.
لم يكن Docker engine متاحًا للفحص أيضًا؛ لم تُشغّل أي خدمة أو تُعد تشغيلها.
لم يُرسل كود إلى خدمة خارجية، ولم تُجرب أي لغة فعليًا. اختبارات المهمة محاكاة معزولة،
وليست شهادة صلاحية لخادم تنفيذ أو لعزله. لا fallback إلى خادم تجريبي عام.

العقد مبني على [توثيق API 1.13.1](https://ce.judge0.com/)
و[إعدادات الإصدار الرسمية](https://github.com/judge0/judge0/blob/v1.13.1/judge0.conf).
يرفض الموصل إصدار API مختلفًا؛ اعتماده يحتاج مراجعة توافق واختبارات صريحة.
اختيار نشر آمن ومحدث وفحص المضيف مطلوبان؛ توافق API لا يثبت أمان إصدار الخدمة.

## الإعدادات

الاتصالات في `settings.LAB_JUDGE0_SERVICES` بمفتاح المحرك المحلي؛ تهيئة البيئة تدعم:

| المتغير | الغرض |
| --- | --- |
| `LAB_JUDGE0_URL` | عنوان خدمة مستقلة موثوقة؛ غيابه يعطّل الاتصال |
| `LAB_JUDGE0_ENGINE_KEY` | مفتاح المحرك، افتراضيًا `primary` |
| `LAB_JUDGE0_AUTH_TOKEN` | سر الخادم، خارج Git والمتصفح ونماذج التحديات |
| `LAB_JUDGE0_AUTH_HEADER` | `X-Auth-Token` أو ترويسة X مخصصة مطابقة للخدمة |
| `LAB_JUDGE0_ALLOW_HTTP` | 1 يسمح HTTP للشبكة المحلية الموثوقة؛ الأصل HTTPS |
| `LAB_JUDGE0_DEDICATED` | 1 إقرار أن الخدمة مخصصة وليست عامة |
| `LAB_JUDGE0_SANDBOX_REVIEW_ID` | مرجع مراجعة المشغل للعزل؛ ليس إثباتًا آليًا |

يمكن ضبط باقي القيم في قاموس الإعدادات الموثوق: اتصال 3 ثوانٍ وقراءة 5، استجابة 4MiB،
كود 400000 بايت، stdin حتى 64KiB، wall حتى 30 ثانية، و32 عملية/خيط.
لا تقبل الخدمات عنوانًا أو ترويسات أو خيارات compiler/network/callback من الطالب.
`LAB_REFERENCE_MAX_SECONDS=60` و`LAB_REFERENCE_MAX_CASES=200` يحدان العمل الإداري.
المدة ميزانية polling؛ قد يضاف طلب شبكة محدود المهلة والفحص النهائي، وليست مؤقت قتل العملية.

قبل إرسال الكود يتحقق الموصل من `/about` و`/config_info` وإقرار الخدمة المخصصة، ويرفض
غياب سقوف الخادم أو تمكين الشبكة أو السماح بتجاوزها. على **خادم Judge0 نفسه** ضبط:
`ENABLE_NETWORK=false` و`ALLOW_ENABLE_NETWORK=false`، وCPU ≤10 ثوانٍ، wall ≤30،
memory ≤524288KiB، max_file_size ≤1024KiB، processes ≤64.
هذه سقوف أولية وليست سعة إنتاج مثبتة. يجب فحص namespaces/cgroups والعزل الفعلي والصلاحيات
والملفات ومنع الخروج الشبكي بجدار حماية وفصل التنفيذ عن Django وأسراره.
قراءة config وإرسال `enable_network=false` لا تثبتان تنفيذ العزل على مستوى النظام.
حد ملف Judge0 بوحدة KiB تقريبي وليس حد stdout دقيقًا؛ الموصل يحد أيضًا حجم الاستجابة
ومجموع stdout/stderr/compile/message بعد فك الترميز.

## الإجراءات الإدارية

الأوامر للتشغيل اللاحق على قاعدة معاينة، ولم تُنفذ على بيانات المشروع.
ACTOR_ID حساب إداري موجود، يتحقق الخادم من نشاطه وstaff وصلاحيته في كل إجراء.

```text
python manage.py lab_judge0 inspect --engine primary
python manage.py lab_judge0 sync --engine primary --actor ACTOR_ID
python manage.py lab_judge0 bind --engine primary --remote-id REMOTE_ID --actor ACTOR_ID
python manage.py lab_judge0 smoke --language LOCAL_ID --actor ACTOR_ID --seconds 30
python manage.py lab_judge0 enable --language LOCAL_ID --actor ACTOR_ID
python manage.py lab_judge0 reference --version VERSION_ID --actor ACTOR_ID --seconds 30
python manage.py lab_judge0 resume --verification JOB_UUID --actor ACTOR_ID --seconds 30
python manage.py lab_judge0 report --verification JOB_UUID --actor ACTOR_ID
```

`courses.manage_lab_runtime` صلاحية مستقلة للمزامنة والربط والفحص والتفعيل، تُمنح صراحة
عبر مجموعة إدارية؛ لا تُسند تلقائيًا ولا تمنح إدارة المستخدمين. فحص المرجع يتطلب staff
وصلاحية مراجعة التحدي العام أو الدورة بحسب النطاق. الفحص ليس اعتمادًا ولا يتجاوز منع المراجعة الذاتية.

`Judge0LanguageDiscovery` يرصد الحضور والاسم دون تفعيل أو تغيير هوية لغة مستخدمة.
الربط يثبت ID واسم اللغة وإصدار toolchain الكامل **لهذه الخدمة**؛ التسميات التي لا تفصل
الإصدار بوضوح تحتاج adapter مراجَعًا. الهوية المستخدمة ولقطات النتائج القديمة لا تُعاد كتابتها.
وجود اللغة ليس إثبات تشغيلها. smoke يتضمن ناتجًا عربيًا صحيحًا وخطأ برنامج وحلقة تبلغ مهلة CPU،
ولا يسجل verified إلا بعد نجاح الثلاثة؛ التفعيل مستقل. البرامج متوفرة لـPython وJavaScript
وJava وC++ فقط، وكلها **مرشحة لم تُجرّب فعليًا بعد**.

## النقل والنتائج الخاصة

`judge0.py` يرسل POST مرة واحدة إلى submissions مع `wait=false` وbase64، ثم يقرأ token
بـGET. لا تشغيل محلي ولا انتظار داخل صفحات Django. expected_output لا يُرسل؛ المقارنة محلية
بسياسة النسخة exact أو توحيد CRLF/CR إلى LF، دون trim أو تجاهل اختلافات.
المصدر والمدخلات والمخرجات UTF-8/base64؛ JSON وBase64 غير الصالحين مرفوضان.
الانتظار والتنفيذ منفصلان عن compile/runtime/time/output/memory limits وعن system_error.
لا يُستنتج تجاوز الذاكرة من SIGSEGV وحده. رسائل الفشل ثابتة ولا تكشف جسم upstream أو الأسرار.
`public_data()` لا يضم source أو output؛ أي واجهة لاحقة تعرض النصوص بـtextContent أو escaping.

## الفحص ودليل النشر

`ReferenceVerification` لقطة خاصة للنسخة والحل والاختبارات والترتيب والمقارنة والحدود،
و`ReferenceVerificationCase` يحفظ حالة كل عملية وtoken ونتيجتها الخاصة.
بصمة النسخة مع execution profile تثبت اللغة والإصدار وإعدادات التنفيذ والقدرات المرصودة
وهوية العنوان المشفرة hash دون أسرار. تغيير profile يبطل الدليل القديم.

يُحفظ dispatching قبل POST، ثم token فور استلامه. مهلة أو انهيار غامض يجعلانها uncertain:
**لا إعادة إرسال تلقائية**؛ يلزم تصالح تشغيلي قبل أي إعادة صريحة. token المحفوظ يسمح بـresume
من خلال GET فقط. لا وعد exactly-once إذا ضاع رد الإنشاء. smoke أيضًا لا يعيد POST تلقائيًا.
lease مشروط يمنع عاملين من معالجة الفحص نفسه. الفحص المعلق لا ينتج passed ويمكن استئنافه.
قبل اعتماد الدليل يعاد فحص اللغة والقدرات والبصمة وحفظه داخل معاملة؛ النجاح يتطلب اكتمال
كل الحالات ومطابقة نتائجها. تغير النسخة ينتج stale. لا تكفي أعلام قديمة أو أدلة بلا profile للنشر.
الخدمات والأوامر للمراجعين المخولين فقط، وتطبع summaries دون الحل أو الاختبارات المخفية.
القدرات المرصودة مخزنة مؤقتًا؛ تغير خدمة بعيدة لا يُكتشف دون probe/sync. التشغيل الحقيقي
يعيد الفحص، ويلزم تشغيل المزامنة ضمن إجراءات إدارة الخدمة عند تحديثها.

ترحيل `0020_judge0_reference_verification` إضافي. لا تعديل لترحيلات قديمة أو بيانات منشورة.
لم يطبق على قاعدة المشروع؛ طُبق داخل الاختبارات فقط. لا واجهات أو مسارات أو طابور طلاب جديد.

## قبل طابور الطلاب

تجهيز خدمة مستقلة وعنوانها وسرها في إعدادات الخادم، وفحص العزل والسقوف فعليًا، ثم تطبيق
الترحيل على قاعدة معاينة ومنح الصلاحيات المحدودة، وsync/bind/smoke/enable لكل لغة، وفحص
مرجعي حقيقي. يلزم لاحقًا طابور موثوق، ومصالحة uncertain، وضبط السعة والتزامن والمراقبة
وسياسة الاحتفاظ بالسجلات؛ هذه الأجزاء ليست ضمن المهمة الحالية.
